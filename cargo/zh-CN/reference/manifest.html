The Cargo Book

清单格式

每个包的 Cargo.toml 文件称为其 清单（manifest）。它使用 TOML 格式编写。其中包含编译该包所需的元数据。有关 cargo 如何查找清单文件的更多细节，请参阅 cargo locate-project 一节。

每个清单文件由以下部分组成：

  • cargo-features — 不稳定、仅 nightly 可用的特性。
  • [package] — 定义包。
    • name — 包的名称。
    • version — 包的版本。
    • authors — 包的作者。
    • edition — Rust 版次。
    • rust-version — 最低支持的 Rust 版本。
    • description — 包的描述。
    • documentation — 包文档的 URL。
    • readme — 包的 README 文件路径。
    • homepage — 包主页的 URL。
    • repository — 包源码仓库的 URL。
    • license — 包的许可证。
    • license-file — 许可证文本的路径。
    • keywords — 包的关键词。
    • categories — 包的类别。
    • workspace — 包所属工作空间的路径。
    • build — 包构建脚本的路径。
    • links — 包所链接的本机库名称。
    • exclude — 发布时排除的文件。
    • include — 发布时包含的文件。
    • publish — 可用于阻止发布该包。
    • metadata — 供外部工具使用的额外设置。
    • default-run — cargo run 默认运行的二进制目标。
    • autolib — 禁用库自动发现。
    • autobins — 禁用二进制目标自动发现。
    • autoexamples — 禁用示例目标自动发现。
    • autotests — 禁用测试目标自动发现。
    • autobenches — 禁用基准测试目标自动发现。
    • resolver — 设置要使用的依赖解析器。
  • 构建目标表：（有关设置，请参阅配置）
    • [lib] — 库目标设置。
    • [[bin]] — 二进制目标设置。
    • [[example]] — 示例目标设置。
    • [[test]] — 测试目标设置。
    • [[bench]] — 基准测试目标设置。
  • 依赖表：
    • [dependencies] — 包库依赖。
    • [dev-dependencies] — 用于示例、测试和基准测试的依赖。
    • [build-dependencies] — 用于构建脚本的依赖。
    • [target] — 特定平台的依赖。
  • [badges] — 在注册表上显示的徽章。
  • [features] — 条件编译特性。
  • [lints] — 为此包配置 linter。
  • [hints] — 为编译此包提供提示。
  • [patch] — 覆盖依赖。
  • [replace] — 覆盖依赖（已弃用）。
  • [profile] — 编译器设置与优化。
  • [workspace] — 工作空间定义。

[package] 小节

Cargo.toml 中的第一个小节是 [package]。

[package]
name = "hello_world" # 包的名称
version = "0.1.0"    # 当前版本，遵循 semver

Cargo 唯一要求的字段是 name。如果要发布到注册表，注册表可能会要求额外的字段。有关发布到 crates.io 的要求，请参阅下面的说明以及发布章节。

name 字段

包名是用于指代该包的标识符。当该包作为依赖列在另一个包中时，会使用它；它也被用作自动推断的库目标和二进制目标的默认名称。

名称只能使用字母数字字符，或 -、_，且不能为空。

请注意，cargo new 和 cargo init 会对包名施加一些额外限制，例如强制要求它是有效的 Rust 标识符且不是关键字。crates.io 施加的限制更多，例如：

  • 只允许使用 ASCII 字符。
  • 不要使用保留名称。
  • 不要使用诸如 “nul” 之类的 Windows 特殊名称。
  • 长度最多为 64 个字符。

version 字段

version 字段按照 SemVer 规范格式化：

版本必须包含三个数字部分：主版本号、次版本号和补丁版本号。

可以在连字符后添加预发布部分，例如 1.0.0-alpha。预发布部分可以用句点分隔，以区分不同组件。数字组件按数值比较，其他内容按字典序比较。例如，1.0.0-alpha.11 高于 1.0.0-alpha.4。

可以在加号后添加元数据部分，例如 1.0.0+21AF26D3。这仅用于提供信息，Cargo 通常会忽略它。

Cargo 内置了语义化版本控制的概念，因此如果两个版本最左侧的非零主/次/补丁分量相同，它们就被认为是兼容的。有关 Cargo 如何使用版本来解析依赖的更多信息，请参阅解析器章节。

该字段是可选的，默认值为 0.0.0。发布包时该字段是必需的。

MSRV： 在 1.75 之前，该字段是必需的

authors 字段

[!IMPORTANT] 该字段已弃用。

可选的 authors 字段以数组形式列出被视为该包“作者”的个人或组织。每个作者条目的末尾可以在尖括号中包含一个可选的电子邮件地址。

[package]
# ...
authors = ["Graydon Hoare", "Fnu Lnu <no-reply@rust-lang.org>"]

该字段会出现在包元数据中，并出于向后兼容性出现在 build.rs 中的 CARGO_PKG_AUTHORS 环境变量中。

edition 字段

edition 键是可选的，它影响包使用哪个 Rust 版次编译。在 [package] 中设置 edition 键会影响包内所有构建目标/crate，包括测试套件、基准测试、二进制目标、示例等。

[package]
# ...
edition = "2024"

大多数清单的 edition 字段由 cargo new 自动填入最新稳定版次。默认情况下，cargo new 目前创建的清单使用 2024 版次。

如果 Cargo.toml 中不存在 edition 字段，则出于向后兼容性假定为 2015 版次。请注意，使用 cargo new 创建的所有清单都不会使用这个历史回退值，因为它们会显式将 edition 指定为较新的值。

rust-version 字段

rust-version 字段告诉 Cargo 你的包支持哪个版本的 Rust 工具链。更多细节请参阅 Rust 版本章节。

description 字段

描述是关于包的简短说明。crates.io 会随你的包一起显示它。它应为纯文本（不是 Markdown）。

[package]
# ...
description = "A short description of my package"

[!NOTE] crates.io 要求设置 description。

documentation 字段

documentation 字段指定一个 URL，指向托管该 crate 文档的网站。如果清单文件中未指定 URL，当文档已构建并可用时，crates.io 会自动将你的 crate 链接到对应的 docs.rs 页面（参见 docs.rs 队列）。

[package]
# ...
documentation = "https://docs.rs/bitflags"

readme 字段

readme 字段应为包根目录中某个文件的路径（相对于此 Cargo.toml），该文件包含关于包的一般信息。发布时，该文件会被传输到注册表。crates.io 会将其解释为 Markdown，并渲染在 crate 页面上。

[package]
# ...
readme = "README.md"

如果该字段未指定值，且包根目录中存在名为 README.md、README.txt 或 README 的文件，则将使用该文件的名称。你可以通过将该字段设置为 false 来抑制此行为。如果该字段设置为 true，则假定默认值为 README.md。

homepage 字段

homepage 字段应为一个 URL，指向作为你的包主页的网站。

[package]
# ...
homepage = "https://serde.rs"

只有当 crate 拥有源代码仓库或 API 文档之外的专用网站时，才应为 homepage 设置值。不要让 homepage 与 documentation 或 repository 的值重复。

repository 字段

repository 字段应为一个 URL，指向你的包的源代码仓库。

[package]
# ...
repository = "https://github.com/rust-lang/cargo"

license 与 license-file 字段

license 字段包含该包发布所依据的软件许可证名称。license-file 字段包含许可证文本所在文件的路径（相对于此 Cargo.toml）。

crates.io 将 license 字段解释为 SPDX 2.3 许可证表达式。名称必须是 SPDX 许可证列表 3.20 中的已知许可证。更多信息请参阅 SPDX 网站。

SPDX 许可证表达式支持 AND 和 OR 运算符来组合多个许可证。1

[package]
# ...
license = "MIT OR Apache-2.0"

使用 OR 表示用户可以选择其中任一许可证。使用 AND 表示用户必须同时遵守两个许可证。WITH 运算符表示带有特殊例外的许可证。一些示例：

  • MIT OR Apache-2.0
  • LGPL-2.1-only AND MIT AND BSD-2-Clause
  • GPL-2.0-or-later WITH Bison-exception-2.2

如果包使用非标准许可证，则可以指定 license-file 字段来代替 license 字段。

[package]
# ...
license-file = "LICENSE.txt"

[!NOTE] crates.io 要求设置 license 或 license-file 之一。

keywords 字段

keywords 字段是一个字符串数组，用于描述该包。这有助于在注册表上搜索该包，你可以选择任何能帮助他人找到此 crate 的词语。

[package]
# ...
keywords = ["gamedev", "graphics"]

[!NOTE] crates.io 最多允许 5 个关键词。每个关键词必须是 ASCII 文本，最多 20 个字符，以字母数字字符开头，且只能包含字母、数字、_、- 或 +。

categories 字段

categories 字段是一个字符串数组，表示该包所属的类别。

categories = ["command-line-utilities", "development-tools::cargo-plugins"]

[!NOTE] crates.io 最多允许 5 个类别。每个类别应与 https://crates.io/category_slugs 中可用的字符串之一匹配，且必须完全匹配。

workspace 字段

workspace 字段可用于配置该包将作为成员加入的工作空间。如果未指定，则会在文件系统中向上查找，推断为第一个包含 [workspace] 的 Cargo.toml。如果该成员不在工作空间根目录的子目录中，设置此字段会很有用。

[package]
# ...
workspace = "path/to/workspace/root"

如果清单中已定义了 [workspace] 表，则不能指定该字段。也就是说，一个 crate 不能同时是某个工作空间的根 crate（包含 [workspace]），又是另一个工作空间的成员 crate（包含 package.workspace）。

更多信息请参阅工作空间章节。

build 字段

build 字段指定包根目录中的一个文件，该文件是用于构建本机代码的构建脚本。更多信息可在构建脚本指南中找到。

[package]
# ...
build = "build.rs"

默认值为 "build.rs"，即从包根目录中名为 build.rs 的文件加载脚本。使用 build = "custom_build_name.rs" 可指定其他文件的路径，或使用 build = false 禁用构建脚本的自动探测。

links 字段

links 字段指定正在链接的本机库的名称。更多信息可在构建脚本指南的 links 一节中找到。

例如，一个链接名为 “git2” 的本机库（例如 Linux 上的 libgit2.a）的 crate 可以这样指定：

[package]
# ...
links = "git2"

exclude 与 include 字段

exclude 和 include 字段可用于显式指定在打包项目以发布时包含哪些文件，以及某些类型的变更跟踪（见下文）。exclude 字段中指定的模式标识一组不包含的文件，而 include 中的模式指定显式包含的文件。

[package]
# ...
exclude = ["/ci", "images/", ".*"]

[package]
# ...
include = ["/src", "COPYRIGHT", "/examples", "!/examples/big_example"]

[!NOTE] 运行 cargo package --list 可验证包中将包含哪些文件。

如果两个字段都未指定，默认包含包根目录下的所有文件，但以下列出的排除项除外。

如果未指定 include，则将排除以下文件：

  • 如果包不在 git 仓库中，则以点开头的所有“隐藏”文件都将被跳过。
  • 如果包在 git 仓库中，则仓库的 gitignore 规则和全局 git 配置所忽略的任何文件都将被跳过。

如果指定了 include，则不会应用仓库的 gitignore 规则和全局 git 配置。

无论指定了 exclude 还是 include，以下文件始终被排除：

  • 任何子包都将被跳过（任何包含 Cargo.toml 文件的子目录）。
  • 包根目录下名为 target 的目录将被跳过。

以下文件始终被包含：

  • 包本身的 Cargo.toml 文件始终被包含，无需在 include 中列出。
  • 经过最小化的 Cargo.lock 会自动包含。更多信息请参阅 cargo package。
  • 如果指定了 license-file，它始终被包含。

这些选项是互斥的；设置 include 会覆盖 exclude。如果需要在 include 的一组文件中再排除某些文件，请使用下文描述的 ! 运算符。

这些模式应采用 gitignore 风格的模式。简要说明如下：

  • foo 匹配包中任意位置名为 foo 的任何文件或目录。这等价于模式 **/foo。
  • /foo 仅匹配包根目录中名为 foo 的任何文件或目录。
  • foo/ 匹配包中任意位置名为 foo 的任何 目录。
  • 支持 *、? 和 [] 等常见 glob 模式：
    • * 匹配除 / 之外的零个或多个字符。例如，*.html 匹配包中任意位置扩展名为 .html 的任何文件或目录。
    • ? 匹配除 / 之外的任意字符。例如，foo? 匹配 food，但不匹配 foo。
    • [] 允许匹配一个字符范围。例如，[ab] 匹配 a 或 b。[a-z] 匹配字母 a 到 z。
  • **/ 前缀表示在任意目录中匹配。例如，**/foo/bar 匹配任意位置直接位于 foo 目录下的文件或目录 bar。
  • /** 后缀匹配其中的所有内容。例如，foo/** 匹配 foo 目录内的所有文件，包括 foo 下各级子目录中的所有文件。
  • /**/ 匹配零个或多个目录。例如，a/**/b 匹配 a/b、a/x/b、a/x/y/b，依此类推。
  • ! 前缀用于否定模式。例如，模式 src/*.rs 和 !foo.rs 会匹配 src 目录内所有扩展名为 .rs 的文件，但名为 foo.rs 的文件除外。

在某些情况下，include/exclude 列表也用于变更跟踪。对于使用 rustdoc 构建的目标，它用于确定要跟踪的文件列表，以判断该目标是否需要重新构建。如果包有一个不发出任何 rerun-if-* 指令的构建脚本，则 include/exclude 列表用于跟踪这些文件发生变化时是否应重新运行构建脚本。

publish 字段

publish 字段可用于控制该包可以发布到哪些注册表名称：

[package]
# ...
publish = ["some-registry-name"]

为防止包被误发布到注册表（如 crates.io），例如为了让包在公司内部保持私有，你可以省略 version 字段。如果希望更明确，可以禁用发布：

[package]
# ...
publish = false

如果 publish 数组只包含一个注册表，则未指定 --registry 标志时，cargo publish 命令将使用它。

metadata 表

默认情况下，Cargo 会对 Cargo.toml 中未使用的键发出警告，以帮助检测拼写错误等。然而，package.metadata 表被 Cargo 完全忽略，不会发出警告。希望将包配置存储在 Cargo.toml 中的工具可以使用这一节。例如：

[package]
name = "..."
# ...

# Metadata used when generating an Android APK, for example.
[package.metadata.android]
package-name = "my-awesome-android-app"
assets = "path/to/static"

你需要查看所用工具的文档，了解如何使用该字段。对于使用 package.metadata 表的 Rust 项目，请参阅：

  • docs.rs

在工作空间层级还有一个类似的表 workspace.metadata。虽然 Cargo 没有规定这两个表内容的格式，但建议外部工具以一致的方式使用它们，例如，如果 package.metadata 中缺少数据，且对相关工具而言合理，则可以引用 workspace.metadata 中的数据。

default-run 字段

清单 [package] 小节中的 default-run 字段可用于指定 cargo run 默认选择的二进制目标。例如，当同时存在 src/bin/a.rs 和 src/bin/b.rs 时：

[package]
default-run = "a"

The [lints] section

Override the default level of lints from different tools by assigning them to a new level in a table, for example:

[lints.rust]
unsafe_code = "forbid"

This is short-hand for:

[lints.rust]
unsafe_code = { level = "forbid", priority = 0 }

level corresponds to the lint levels in rustc:

  • forbid
  • deny
  • warn
  • allow

priority is a signed integer that controls which lints or lint groups override other lint groups:

  • lower (particularly negative) numbers have lower priority, being overridden by higher numbers, and show up first on the command-line to tools like rustc

To know which table under [lints] a particular lint belongs under, it is the part before :: in the lint name. If there isn’t a ::, then the tool is rust. For example a warning about unsafe_code would be lints.rust.unsafe_code but a lint about clippy::enum_glob_use would be lints.clippy.enum_glob_use.

For example:

[lints.rust]
unsafe_code = "forbid"

[lints.clippy]
enum_glob_use = "deny"

[lints.cargo]
unused_dependencies = "deny"

Generally, these will only affect local development of the current package. Cargo only applies these to the current package and not to dependencies. As for dependents, Cargo suppresses lints from non-path dependencies with features like --cap-lints.

See also the lints chapter for the available lints emitted by Cargo itself.

MSRV: Respected as of 1.74

The [hints] section

The [hints] section allows specifying hints for compiling this package. Cargo will respect these hints by default when compiling this package, though the top-level package being built can override these values through the [profile] mechanism. Hints are, by design, always safe for Cargo to ignore; if Cargo encounters a hint it doesn’t understand, or a hint it understands but with a value it doesn’t understand, it will warn, but not error. As a result, specifying hints in a crate does not impact the MSRV of the crate.

Individual hints may have an associated unstable feature gate that you need to pass in order to apply the configuration they specify, but if you don’t specify that unstable feature gate, you will again get only a warning, not an error.

There are no stable hints at this time. See the documentation for the unstable mostly-unused and min-opt-level hints.

MSRV: Respected as of 1.90.

The [badges] section

The [badges] section is for specifying status badges that can be displayed on a registry website when the package is published.

[!NOTE] crates.io previously displayed badges next to a crate on its website, but that functionality has been removed. Packages should place badges in its README file which will be displayed on crates.io (see the readme field).

[badges]
# The `maintenance` table indicates the status of the maintenance of
# the crate. This may be used by a registry, but is currently not
# used by crates.io. See https://github.com/rust-lang/crates.io/issues/2437
# and https://github.com/rust-lang/crates.io/issues/2438 for more details.
#
# The `status` field is required. Available options are:
# - `actively-developed`: New features are being added and bugs are being fixed.
# - `passively-maintained`: There are no plans for new features, but the maintainer intends to
#   respond to issues that get filed.
# - `as-is`: The crate is feature complete, the maintainer does not intend to continue working on
#   it or providing support, but it works for the purposes it was designed for.
# - `experimental`: The author wants to share it with the community but is not intending to meet
#   anyone's particular use case.
# - `looking-for-maintainer`: The current maintainer would like to transfer the crate to someone
#   else.
# - `deprecated`: The maintainer does not recommend using this crate (the description of the crate
#   can describe why, there could be a better solution available or there could be problems with
#   the crate that the author does not want to fix).
# - `none`: Displays no badge on crates.io, since the maintainer has not chosen to specify
#   their intentions, potential crate users will need to investigate on their own.
maintenance = { status = "..." }
